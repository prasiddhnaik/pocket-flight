Agent flight interface

13 October 2026 · Pocket Flight · Design for review

Agreed scope: stepped simulation by default, optional continuous live flight, precise commands plus physical pilot maneuvers, local development only. This document describes proposed behavior; the interface has not been implemented.

1. Intended outcome

An AI agent can select any of the four aircraft, start an island flight, send commands, advance simulation, observe the result, and perform takeoff, waypoint flight and landing through a supported programmatic interface. It does not need to synthesize keyboard events, manipulate touch controls, or inspect pixels to obtain basic flight state.

Human inputs and agent commands feed the same physics, contact, damage and mission updates. A pilot maneuver changes throttle and control-surface commands on each simulation tick. Its success depends on the resulting aircraft motion.

Player input / agent command / pilot controller → shared flight update → aircraft motion, collision, mission events, replay and telemetry

First-release flight limits remain subsonic around the island with the current 1,800 m ceiling. Detached debris remains visual. The public version 21 release, broad Settings redesign, high-altitude flight and supersonic flight are outside this local change.

The recommended core API can support a standalone MCP server later. The first version includes browser WebMCP tools and a loopback development bridge, which is usable with a small Bun client without browser-specific scripting.

3. Agent session and control ownership

  • An agent session identifies one game instance, its aircraft, simulation clock, configuration and active maneuver. Only one controller owns that aircraft at a time.
  • Starting a session awaits the aircraft and world assets, then uses a declared runway-departure or trimmed airborne start. Reset is an explicit operation.
  • The screen shows that an agent is flying, its active maneuver, and a Take control action. A human takeover cancels the active agent operation, clears its commands and hands back the existing physical aircraft state.
  • Agent runs are tagged in recordings and results. They do not earn human medals or write entries into the player's flight log. Player assistance and configuration preferences are restored on handback rather than overwritten persistently.
  • Pause, restart, leaving the flight, closing the page, and disposal terminate or suspend operations consistently. A stale session identifier cannot command a replacement aircraft.
  • Mutating commands are serialized. A low-level command cancels the active maneuver and reports that cancellation.

4. Simulation clock

Stepped mode — default

The aircraft advances only when an agent requests a step. A request applies precise commands or the active pilot maneuver for a bounded amount of simulation time. Physics uses its existing 120 Hz substeps inside the common 60 Hz game update. Mission logic, events, replay, control surfaces and simulated aircraft animations advance through that same update.

Each request is rounded to whole 60 Hz game-update ticks, is limited to five simulated seconds, and returns the actual time advanced. Each game-update tick includes the existing 120 Hz physics substeps. Work is chunked so cancellation and human takeover can interrupt it. Rendering and UI remain responsive between steps. A crash or completed flight can end a request early.

Live mode — optional

The same command source or pilot controller advances with the normal game clock. Precise command holds have an explicit duration; when their duration ends, live flight pauses and reports expiration. A maneuver has a simulation-time deadline and explicit running, completed, failed or cancelled status. Normal page visibility and pause behavior still apply.

Switching clocks resets render accumulator timing so elapsed wall time cannot become an unexpected physics jump. Agent thinking time has no effect on stepped flight time.

5. Public command contract within local development

The following names describe the proposed versioned contract. Results are JSON-serializable, include the session ID and simulation tick, and acknowledge the actual effect. Read operations do not advance time.

OperationInputs and effectResult
get_flight_capabilitiesRead aircraft, runway and scenario IDs; supported commands; clock limits and units.Catalog, declared aircraft envelope and interface version.
start_agent_flightSelect aircraft, scenario, clock, assistance, loading and wind preset. Initialize a named agent session after assets are ready.Session ID, initial observation and effective configuration.
read_agent_flightRead the current session.Telemetry, world context, command targets and maneuver status.
advance_agent_flightAdvance up to five simulated seconds in stepped mode using precise commands or the active maneuver.Final observation, events collected across every update, actual duration and termination reason.
set_agent_commandsSet throttle, pitch, roll, rudder and brakes; in live mode include the command hold duration.Accepted commands and the effect on any active maneuver.
set_aircraft_configurationCommand gear, flap preset and trim through normal actuator targets.Accepted targets, current positions and any rejected aircraft-specific actions.
start_flight_maneuverStart takeoff, fly-to, hold or landing with validated targets and an explicit deadline.Maneuver ID and running phase; acceptance does not claim completion.
cancel_flight_maneuverCancel the active maneuver and pause live agent flight.Cancellation reason and final observation.
set_agent_clockChange between stepped and live mode.Effective clock and pending-operation status.
reset_agent_flightExplicitly reset the agent session to a named start scenario.New run identity and initial observation.
release_agent_controlCancel agent operations and hand control back to the player, initially paused.Handback state with commands cleared.

Throttle is an absolute target from 0 to 1; pitch, roll and rudder commands are normalized from -1 to 1; trim is from -1 to 1; brakes are boolean. The adapter translates these into the physical command path. Gear is up/down and flaps use the aircraft's supported presets. Finch's fixed gear and absent movable flaps are reported explicitly. Ground gear retraction remains blocked.

Missing attitude commands default to neutral in a new precise command request. Throttle and configuration targets persist until replaced. Non-finite values, invalid IDs, unknown fields, unsupported actions and expired session IDs return structured errors.

6. Physical pilot maneuvers

The pilot controller consumes aircraft telemetry and world geometry, calculates desired flight behavior, and outputs bounded physical commands on every simulation update. It uses aircraft-specific stall speed, trim, rotation guidance, loaded mass, actuator state and propulsion response. It does not write an aircraft's pose or velocity during a maneuver.

ManeuverPhasesCompletion and failure
TakeoffRunway alignment, acceleration, rotation and climb-out.Complete after supported liftoff and a stable climb with clearance and airspeed margins. Report crash, timeout, insufficient available runway or inability to climb as failure.
Fly to waypointPlan a feasible island route, track heading/altitude/airspeed, then capture the target.Complete within declared position and altitude tolerances. Reject targets outside the island envelope and report blocked or unreachable routes.
HoldMaintain a declared heading, altitude and airspeed.Continue until cancelled or the requested simulation duration ends; expose tracking errors and envelope limits.
LandChoose runway direction, approach setup, alignment, descent, flare, touchdown and braking.Complete only after wheel-supported touchdown on the requested runway and ground speed below 1 m/s. An unstable approach attempts a physical go-around if feasible; otherwise it reports failure and pauses.

Landing and route feasibility use the current aircraft's envelope and world terrain/scenery, with conservative clearance. A maneuver is allowed to report failure rather than claim an impossible goal was completed. Initial calibration order remains Aurelia, Finch, Peregrine, then Stormbird.

Assistance mode is explicit in telemetry. The pilot controller and precise commands must both work through the selected physical command interpretation; using beginner assistance is disclosed and does not change the underlying force/contact engine.

7. Observations and world context

  • Aircraft ID, interface/physics version, session/run IDs, simulation tick, simulation time, clock and control owner.
  • World position and velocity, quaternion, body angular rates, heading, pitch, roll, airspeed, ground speed, vertical speed and altitude above ground.
  • Angle of attack, sideslip, Mach, stall flag, current stall speed, wind vector, fuel, loaded mass and balance information.
  • Throttle target and engine power; actual control-surface, gear and flap positions; trim; wheel contact loads and ground state.
  • Health, component damage, detached wing flags, engine-out state and crash/flight result.
  • Maneuver phase, target, tracking errors, time remaining, completion/failure reason and events across the requested step.
  • Runway positions, elevation, orientation, width and length; local terrain/obstacle queries needed for route and landing decisions.

Use metres, metres per second and seconds. Expose headings and attitude angles in degrees with explicitly documented axes: world X points east, Y is altitude, and positive Z points south; heading 0° is north and 90° is east. Body angular rates retain radians per second and are labeled. Observations report commanded and actual actuator states separately.

8. Local access and lifecycle

Expose the typed API only in Vite development. Register equivalent browser tools through feature-detected document.modelContext.registerTool, and unregister them using an AbortSignal during disposal. The production build does not register agent tools, expose the agent API or include the agent-control UI.

A Vite development plugin provides a loopback-only command bridge at /__flight_agent. It discovers connected local game sessions and forwards a command to one selected session using Vite's development WebSocket. Replies are correlated by request ID, bounded by a timeout and cancelled when a session disconnects. The bridge rejects non-loopback peers and unrelated browser origins.

A Bun client calls that bridge to let a terminal agent discover sessions, start flight, request maneuvers, advance, read state and stop. This is an application command transport, so no keyboard or touch event synthesis is needed. WebMCP and the Bun client invoke the same validated API methods.

Feature detection reports native browser-tool availability. Unsupported browsers still retain the typed local API and loopback bridge. Disconnects, cancellation and component cleanup clear pending requests and invalidate session ownership.

10. Acceptance evidence to record during execution

  1. Build the local game and private lab without changing the public publication.
  2. Use structured commands to operate all four aircraft in alphabetical order. Record actual takeoff, waypoint and landing phase outcomes and telemetry, including any failures.
  3. Demonstrate stepped thinking time does not move the aircraft; compare equal fixed-tick command sequences for repeatability.
  4. Demonstrate the same controller in optional live mode, with command expiry, pause, cancellation and human takeover.
  5. Confirm HUD, cockpit displays, mission events and replay agree with the commanded flight, and that agent runs do not add human rewards or alter persisted controls preferences.
  6. Confirm development bridge and browser tools are absent from a production build.

No tests have been added or run for this proposed interface. These are acceptance criteria, not claims of completed verification.
