12 October 2026 · Scope agreed; implementation sequence prepared · TypeScript, Three.js math, React, Bun

Build a small aircraft simulation that turns aerodynamic forces, engine thrust, gravity, and ground reactions into believable flight. Weight, loading, control surfaces, and landing gear should explain the aircraft's behavior. Keyboard controls should remain usable through optional, bounded assistance.

Recommended direction

Continue the custom aircraft dynamics already being developed in pocket-flight-site. Use one authoritative rigid body state and one owner for motion integration. Start with Aurelia, establish a trustworthy airborne model and stable wheel contact, then complete Finch, Peregrine and Stormbird in alphabetical order. Aurelia's initial slice includes jet spool, retractable gear and flap configuration, so those systems enter the reference-aircraft milestone.

Use whole-aircraft aerodynamic coefficients initially: lift, drag, side force, and pitch/roll/yaw moments. This gives us a model we can inspect and tune with the available data. Add forces for individual components when a specific behavior needs them. Component mass accounting and component aerodynamic forces are separate choices; estimating a mass budget does not require solving airflow around every part.

Keep Rapier as an explicit collision option to evaluate during the collision phase. Its documentation provides both a complete dynamics pipeline and geometric queries. If we use queries with our integrator, collision response remains our responsibility. If we adopt its dynamic body solver, Rapier becomes the sole motion integrator. [8] [9] [10]

First release scope

The first release supports subsonic flying around the existing island and airfields: takeoff, climbing, turns, approaches, landings, crosswind and engine-out scenarios. Use the current 1,800 m game ceiling as the initial world boundary. The physics model's supported operating envelope and the game's world boundary should be documented separately.

Choose a validated speed/loading range for each aircraft during baseline calibration. Mach below one defines subsonic speed, but does not establish that every aircraft model is accurate throughout that range. Set the supported maximum using the available coefficient/engine data and recorded maneuver results; do not infer validity from a lookup table extending to a higher altitude or speed.

Automatic gear/flap operation starts enabled for new players. Settings → Controls allows manual operation, independently of beginner flight assistance. Aircraft-specific deployment speeds and flap presets come from the calibrated configuration data. Preserve the current island, runway geometry and gameplay routes while measuring their compatibility with the improved flight model.

Later work: the broader Settings redesign, high-altitude flying and supersonic flying are tracked in the redo backlog. Existing developer benchmarks may exercise wider conditions; they do not expand the accepted game-release scope.

Automatic versus manual gear and flaps

The physical configuration is shared: gear position changes drag and ground contacts; flap deflection changes lift, drag and pitching behavior. The decision is who commands that configuration and when. Manual controls add pilot choice; automatic controls add a deployment policy. Flap effects depend on the particular aircraft, as described in the FAA Airplane Flying Handbook, chapter 12.

How the model will work

Start with forces and units

Forces change linear velocity. Moments change angular velocity. Flight should emerge from those changes. NASA's lift and drag equations connect airspeed, density, wing area, and coefficients; JSBSim documents the buildup of forces and moments across six axes. [5] [6] [7] [1]

v_air = v_world − wind_world q̄ = ½ ρ |v_air|² Lift = q̄ S C_L Drag = q̄ S C_D C_D = C_D0 + C_L² / (π AR e) + configuration contributions a_world = total_force_world / mass angular_acceleration_body = I⁻¹ (moment_body − ω_body × (I ω_body)) moment_from_offset_force = r_body × force_body

Use SI throughout: metres, kilograms, seconds, radians, newtons, and newton metres. Keep the existing local aircraft frame: +X right, +Y up, +Z aft. World height is +Y and the map lies in X/Z. Document every frame transform and input sign. Convert aviation forward/right/down conventions explicitly when importing data.

One state, one clock, one integrator

Store center-of-mass position, world velocity, normalized orientation quaternion, body angular velocity, loading/fuel, and actuator state. Derive mesh position from CG and orientation. Make the policy for changing CG during fuel burn explicit so a mass update does not introduce an artificial position jump.

Use integer ticks and fixed 1/120-second dynamics steps initially. Keep the current 60 Hz outer loop while establishing the baseline; move clock ownership only when the regression trace supports it. Bound work during a long frame, document how lost wall time is handled, and retain pose interpolation. Input changes and environmental updates used by a reproducible scenario should be indexed by simulation tick.

Require reproducibility within a recorded runtime and model version. Cross-browser bit-for-bit equality is a separate requirement: even Rapier's deterministic engine can receive different externally computed values, and its documentation specifically discusses the limits of JavaScript transcendental functions. Keep pose-based saved replays usable. [11]

Aerodynamics and aircraft data

Reuse the coefficient model and check signs and force directions first. Establish credible lift/drag curves, side force, stability and damping derivatives, actuator authority, engine spool, thrust, configuration drag, and trim. Use smooth post-stall curves with declared limits. Optional ground effect comes after stable contact and calibration.

Give each model parameter a source or label: measured geometry, engineering estimate, lab result, or gameplay tuning. Record a model version and data revision with telemetry. Review the pitch stability treatment and loading changes across the declared CG envelope. Avoid counting a tail contribution twice when later adding individual tail forces to whole-aircraft moments.

Assistance through actuators

Extract assistance into a bounded controller that requests surface deflections. Apply deflection and rate limits; insufficient airspeed or a stall should reduce available authority through the physical model. Manual and assisted modes share the same aircraft data and integrator. The surface animations already follow solved physics outputs in the newer checkout.

Configuration control has a separate automatic/manual mode selected in Settings → Controls. Both sources issue target gear/flap positions through the same actuator and contact model. A flight-assistance change must not alter this configuration mode.

Ground and collision strategy

For each wheel, evaluate the contact location relative to CG, terrain normal, penetration/compression, and point velocity including angular motion. Compute a nonnegative spring/damper reaction, rolling resistance, steering, braking, and friction bounded by normal load. Apply force and torque through the body. Use static friction or a suitable constraint at low speed so a parked aircraft does not creep. Treat retracting gear and fuselage/wing contacts explicitly. JSBSim's ground-reaction model provides a useful reference for spring, damping, and friction structure. [2]

Accepted crash and damage behavior

The aircraft body remains the physical object throughout contact and damage. Ground and scenery contacts produce measurable normal loads, closing speeds and impulses. Use those measurements with explicitly tuned gameplay thresholds to choose the damaged part and severity. Damage changes the relevant lift, drag, control authority, thrust or gear response on the next physics step.

Risks and practical limits

RiskResponse
Divergent, active checkoutsRecord and reconcile local work before choosing a baseline. Use current working-tree hashes, not a historical commit alone.
Credible equations with invented parametersDeclare data provenance, uncertainty and supported envelopes. Measure geometry and calibrate dynamics; keep estimated data visible in developer documentation.
Stiff suspension is unstableChoose spring rates from static deflection and damping from mass/stiffness. Measure convergence. Use smaller contact steps, an implicit treatment or a constraint solver if the explicit approach misses stability/performance targets.
Two systems advance the same aircraftMake solver ownership part of the collision decision. Forces and contact response feed the selected integrator.
Wing model data is used beyond its limitsTag lab results with geometry revision and operating conditions. Treat stall and whole-aircraft moments with separately justified data.
Physical changes break game routesReview runway distance, air-start speed, mission prompts, landing windows and score thresholds after tuning. Maintain easy assisted keyboard control.
State/replay inconsistenciesVersion full diagnostic traces separately from visual replay. Update all initialization callers and interpolation adapters deliberately.
Scope grows into a general engineLet the selected aircraft behaviors drive the modules. Revisit generic engine features only if the user chooses reuse across games.
