11 October 2026 · Design for review · Pocket Flight aircraft research

Private aerodynamic test lab

Purpose: test the aircraft's aerodynamics so we can improve its geometry and flight data. This is a local research tool for the user and Codex. It is separate from the player-facing game.

Agreed scope

The supported fleet is Finch, Peregrine, Aurelia and Stormbird. The user expanded the scope during implementation. The user selected geometry-based wing analysis. We will load each aircraft’s actual exported geometry, build a numerical lifting-surface representation, run controlled experiments, and display results in a modeled enclosed wind tunnel. The chamber makes the experiment inspectable; the solver and its validation produce the evidence.

Analysis approach

Start with a steady, incompressible vortex-lattice wing model. It predicts attached-flow lift distribution and induced drag from wing planform, incidence and the stated camber treatment. This provides a meaningful step beyond reproducing the game's existing coefficient estimates. MIT's AVL documentation provides a reference for lifting-surface analysis; NASA's modified vortex-lattice model explains why viscous section data is needed for nonlinear lift and stall.

A browser coefficient bench would be faster to build but would only test our current assumptions. Full viscous CFD would address more aircraft and tunnel effects, but requires a suitable volume mesh, boundary conditions, solver convergence, and more substantial validation. Geometry-based wing analysis is the selected first stage.

Use a conservative small-angle operating range initially. Results outside the declared range must show an unsupported-condition state. The custom wing's camber assumptions and geometric extraction conventions accompany each result. No stall prediction will be invented from a linear solver.

Private interface and experiments

  • A separate local entry point launched with Bun, with its own Vite configuration and build output. No game navigation link or player feature is added.
  • Orbitable 3D chamber, selectable full-size aircraft models, adjustable pitch rig, and a clearly identified wing-analysis overlay.
  • Controls for airspeed, angle of attack, and atmosphere/density. The aircraft's pose and the numerical input use the same angle state.
  • Readouts for dynamic pressure, wing lift, induced drag, CL, CDi, lift distribution, and solver status. Units are always visible.
  • Automatic angle sweeps, convergence checks, and CSV/JSON export containing geometry revision, model assumptions, conditions, and results.
  • Flow lines derived from the computed wing velocity field. Decorative fan motion is distinct from calculated aerodynamic evidence.

3D environment

Model an industrial test chamber with a contraction inlet, flow-straightener grid, observation windows, instrumented support rig, service rails, structural ribs, and a downstream fan/diffuser. Cool neutral metal, warm task lighting, and restrained cyan measurement accents make the aircraft and flow readable. This palette gives the room a technical identity while keeping force overlays legible.

Save an editable Blender source and a compact GLB environment. Use a cutaway or transparent observation wall for the default camera. The decorative chamber dimensions must fit all four aircraft and their test angles. The initial numerical boundary is freestream; enclosure wall effects remain explicitly excluded.

The lab reads shared aircraft assets but remains independent of flight missions, game state, replay, and player progression. Unsupported or ill-conditioned geometry must produce a useful error, not plausible-looking fabricated measurements.

Acceptance evidence

  1. Geometry extraction matches runtime span, area, chord and coordinate conventions. The analysis surface is visible over the loaded wing for inspection.
  2. A symmetric flat wing gives approximately zero lift at zero incidence and a symmetric lift distribution. Positive and negative incidence produce the correct force signs.
  3. A benchmark wing agrees with accepted attached-flow theory within a documented tolerance; increasing panel resolution shows convergence. Check the linear-system residual.
  4. Force scales with density and speed squared; dimensionless coefficients remain consistent at identical nondimensional conditions.
  5. Induced drag is nonnegative and is checked against the ideal finite-wing relationship, using the declared conventions.
  6. The visual flow uses the computed vortex field. Solver-invalid cases are visibly flagged. The screen does not label induced drag as total drag.
  7. The browser loads without WebGL/runtime errors, controls change the visible experiment, sweep/export work, and the room remains usable at desktop and narrower widths.
  8. The Blender source, exported GLB, test evidence, and an HTML verification report are preserved locally.

Later work

Add tail and other lifting surfaces, control deflections, validated airfoil polars, viscous drag estimates, stability derivatives and whole-aircraft moments. Introduce tunnel-wall corrections or CFD only with appropriate boundary conditions and validation. Feed accepted results into aircraft design data through an explicit reviewed change, rather than silently retuning the game.
