1. What already works, and where effort remains

The editor already imports models, images, and audio; supports primitives and lights; exposes position/rotation/scale and World/Aircraft anchoring; provides transform and camera keys; offers visibility ranges; and saves projects with portable asset backups. The next changes should improve these flows instead of duplicating them.

3. Recommended first upgrade: placement tools

This is a proposed bounded extension to the existing Object inspector and pose-edit flow. It can use existing transform serialization and history; it does not require a new project-file format. Existing backups should retain their current meaning.

LocatePlace beside aircraft at the current film moment, then frame the selection.
SizeRead current dimensions and set its largest dimension in meters.
GroundAdjust height using the transformed bottom bound and the ground surface.

Place beside aircraft

Proposed behavior: at the current playhead, move the selected object to a fixed offset in the aircraft’s local frame. Preserve its rotation, scale, and anchor. Frame the object after placement so the result is visible in Scene mode.

Sample the same interpolated aircraft pose used by the renderer, rotate the offset by its quaternion, add its world position, and convert the result into the object’s current anchor. This avoids the existing world-X-only placement behavior. The implementation should obtain the rendered subject pose where possible so suspension and interpolation agree.

targetWorld = aircraftPosition + aircraftRotation × localOffset
newPosition = convert targetWorld into the selected object's anchor

The final offset should be a small project default; the first version does not need a new placement preset library. This command moves the selected instance, rather than changing the default size or moving the aircraft.

Dimensions and target size

Proposed behavior: show Width, Height, and Depth in meters for the selected object and add one numeric command: Largest dimension. Entering 30 meters scales the object uniformly until its largest measured dimension reaches 30 meters.

Measure bounds in the object’s anchor frame at the current evaluated pose. This keeps measurement axes stable for World objects and local to the aircraft for Aircraft objects. Label the frame so dimensions are not mistaken for authored Blender-local geometry extents. Proportional scaling preserves the existing relative X/Y/Z scale ratios.

factor = requestedLargestDimension / currentLargestDimension
nextScale = currentScale × factor

Use the current evaluated transform and enforce the same valid-scale limits as other edits. For embedded animated models, displayed dimensions can vary with the sampled pose; show that they describe the current pose instead of promising a fixed envelope over the whole animation.

Place on ground

Proposed behavior: for a selected, unlocked, World-anchored visual object, adjust only its height until the bottom of its transformed bounds rests on the computed ground surface. Preserve X/Z, rotation, and scale.

Use the existing ground/terrain functions in world coordinates, including the runway/apron heights where they apply. Compute a world-space Box3 after the current transform and animation pose have been evaluated. Account for the centered imported pivot, and sample the ground beneath the projected bounding footprint rather than only the object’s center.

heightDelta = max(sampledGroundHeights) − worldBounds.min.y
nextLocalY = currentLocalY + heightDelta (World anchor)

Scope: this is ground placement against the terrain/ground model. It does not snap to the roof of an imported building or every rendered scenery mesh. Sampling the footprint is an approximation on sloped terrain; the command places the bounding bottom above sampled ground rather than solving exact mesh contact. Water uses the ground helper’s zero-height surface, not a gameplay collision claim.

Editing behavior shared by all three tools

  • Enable commands only with a selected, loaded, unlocked visual object and an active flight clip. Keep placement unavailable during playback and export.
  • Use the existing pose-edit handler: a static object updates its transform; an animated object creates or updates a key at the playhead. Make that effect visible in the inspector.
  • Use one committed edit per action so Undo returns to the previous pose. Changing input text before submission should not produce a stack of edits.
  • Do not let dimension measurement or placement fight an active gizmo drag.
  • Keep ground placement unavailable for Aircraft-anchored objects; attaching something to a flying aircraft and grounding it are different intents.
  • Use the Object inspector for these controls and retain numeric transforms as the fine-adjustment path.

Acceptance criteria

  1. A centered and scaled tower can be placed on runway ground without burying its base; a rotated model uses its transformed bounds.
  2. Placing beside a turning aircraft follows its local orientation at the playhead, rather than the world X axis.
  3. A requested target dimension preserves proportions, respects valid scale limits, and appears correctly in Rendered preview.
  4. Static and keyed objects follow the documented edit semantics. Undo/Redo restores each action.
  5. Hidden/out-of-range, locked, unprepared, or missing-asset cases are handled without silently committing invalid transforms.
  6. Save/reopen and backup/restore retain the resulting transforms. Existing projects remain loadable.
  7. Focused placement tests pass; an actual in-app editor session verifies the commands, camera view, focus, and rendered result. A short exported video is inspected separately.

4. Next capabilities and design dependencies

Keyframe editing before a curve editor

Add an editable time field, Copy key, and Move key before introducing a full curve editor. Keep timestamp sorting and the existing interpolation semantics. If a move lands on another key, reject the move with a clear conflict message rather than silently overwriting it. Dragging should preview movement and commit once on release.

Object keys use film seconds; camera keys use source seconds. Camera controls should display both the recording time and its mapped position in the film. Decisions about moving whole clips together with object events belong to a later explicit linking model.

Multi-selection before reusable collections

Start with Shift-select, clear selection, delete/duplicate as one operation, and shared visibility settings. A transform group needs an explicit pivot and a policy for World versus Aircraft anchors. Prefer transforming in world space and converting each result back to its own anchor; define how animated selections receive keys. Persistent parent/child scene hierarchies are a larger design change.

Camera path visualization before dynamic targeting

Draw a sampled camera path, key markers, and target lines in Scene mode only. Convert source-time keys through their selected clip and account for the current camera anchor. Export should exclude these helpers. Dynamic targeting of an imported object needs a stable object-ID reference, a deleted-target fallback, validation, and backup compatibility.

Waveforms before audio automation

Create a cached, downsampled waveform from decoded AudioBuffers and show it on the same film-time scale as sound-layer ranges. Add timeline markers for beats or narration cues. The current volume and fade controls already cover basic mixing; automatic ducking or arbitrary envelopes require a separate audio-automation design.

Billboards and overlays have different purposes

A billboard remains a 3D scene object and faces the camera, so depth and occlusion still apply. A 2D overlay sits in video coordinates and must produce the same result in preview and capture. Treat these as separate additions rather than a single ambiguous “keep image visible” toggle.

Measure export performance before changing the renderer

A short readiness/performance pass can report observed preview cadence at the chosen resolution and the MIME type the browser would select. It is a recommendation aid, not a promise about the encoded frame rate. Offline frame rendering or export queues would require a separate capture architecture and should be evaluated as their own project.
