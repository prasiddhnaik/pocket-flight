CI/CD pipeline design

Pocket Flight · repository prasiddhnaik/pocket-flight · Vercel project pocket-flight · 12 November 2026 · status: design, not built

Purpose

Nothing broken reaches the live site. Every change has to prove that the game starts, the physics behaves and the pilot fits each cockpit before it can reach main, and Vercel only publishes main.

Why now: on 12 November a push that passed every local check failed on Vercel. A published doc linked to images in git-ignored folders, which exist on the developer's Mac but not in a clean checkout. Nothing checked the change between the push and the deploy.

Current state

  • Vercel builds every push. A push to main goes straight to production; other branches get preview URLs. Previews are behind Vercel login (SSO protection on all deployments except custom domains).
  • No CI. main is unprotected and changes are pushed to it directly. Repository auto-merge is off. The repository is public, so branch protection and Actions minutes are free.
  • Checks that exist locally: bun run build (typecheck, Vite build, production docs link check), bun run test (853 tests, about 2.5 minutes), bun run repo:check, and bun run fit all (pilot fit for the F-15C, Peregrine, Stormbird and Aurelia; all four are currently NEAR PASS).
  • The game exposes window.pocketFlight for browser checks only in development builds (src/app/App.tsx). scripts/check-pilot-browser.js and scripts/run-pilot-check.ts already drive the game through it with Playwright.
  • Some checks read git-ignored folders. The fit tool and tests/cockpit-fit-map.test.ts load assets/<id>/cockpit/fit-map.json, and /assets/ is ignored. tests/heron-realism.test.ts and tests/f15c-flight.test.ts also refer to assets/ or output/. These pass locally only because the files happen to exist.

Goals, non-goals, anti-goals

Goals

  • A pull request merges into main only when every check below has passed.
  • The checks run on a clean checkout with the same install and build commands Vercel uses.
  • All six aircraft and the Finch attack variant are checked for startup, a short flight and pilot fit.
  • A green pull request merges itself. Whoever opened it watches it until it is green, fixing failures along the way.

Non-goals

  • Changing flight tuning, physics or visuals. The checks only observe.
  • Rebuilding aircraft or cockpits in CI. Blender does not run in CI; the checks read the committed models.
  • Checking the private wind tunnel (lab/). It is not deployed. Adding bun run lab:build later is optional.

Anti-goals (this fails even if it technically works)

  • A change reaches the live site without passing the checks, including the owner's own pushes.
  • Flaky checks that fail at random, so people learn to rerun until green.
  • Secrets or deploy tokens stored in GitHub when they are not needed.

How a change flows

  1. Work happens on a branch. The author (owner or agent) opens a pull request and turns on auto-merge (gh pr merge --auto --squash).
  2. GitHub Actions runs the checks on the pull request. Vercel builds a preview as it does today; the checks do not depend on it.
  3. The author watches the pull request until it is green. If a check fails, the author fixes it on the same branch and the checks run again.
  4. When every required check is green, GitHub squash-merges the pull request into main and deletes the branch.
  5. Vercel builds main and publishes it to production, unchanged from today.

Direct pushes to main are refused, for admins too.

The checks

One workflow, .github/workflows/ci.yml, triggered on pull requests to main and on pushes to main. Bun is installed with oven-sh/setup-bun, at the version in use locally (1.3.x). Every job installs with bun install --frozen-lockfile. The final job is named CI passed; branch protection requires only that one.

Extending the fit check to the Finch and the Heron

  • The Finch and the Heron have no detail cockpit or fit map; the pilot sits in the airframe model (finch-u2.glb, heron-ut9.glb). Their fit uses the airframe's own seat, canopy glass and controls.
  • Finch, in outside views: the helmet stays under the canopy glass, the back rests on the seat, the hips are no more than about 3 cm into the cushion, and the hands reach their grips. The boots are allowed to fall short of the pedals, which is the 12 November decision for this airframe.
  • Finch, in the seat view: hands and feet reach the controls, as tests/pilot.test.ts already checks.
  • Heron: the same clipping, reach and screen checks as the jets, against its moved front seats.
  • The 12 November one-off scripts (output/pilot-fit-work/finch*.ts) show the canopy, cushion and seat-back measurements to build on.

Game test hook in production builds

Job 4 tests the same build Vercel would ship, so the production build has to expose the test hook. window.pocketFlight is set in production only when the page URL carries ?e2e=1; development keeps it as now. Players never see it.

Working rules for people and agents

  • Never push to main. Branch, open a pull request, turn on auto-merge, and watch it until it merges.
  • A failed check is fixed on the branch, never bypassed. If a check itself is wrong, fixing the check is its own reviewed change.
  • Update AGENTS.md (replace "a push to main deploys to production" with the pull-request rule) and the README's Hosting section.

Left to the builder

  • Exact flight bounds per aircraft. Take them from the existing flight models and tests, not new tuning.
  • Where the fit maps live once tracked: commit them, or move them next to each aircraft's cockpit files. Then find and fix every other check that reads git-ignored folders. The first CI run will list them.
  • Caching (Bun install cache, Playwright browser cache) and job timeouts.
  • Whether job 4 runs the seven variants in one browser session or separately.

Risks

  • Software WebGL is slow on CI runners. Startup may take far longer than on a Mac. Use generous timeouts and judge by simulation state, not frame rate. A check that fails at random must be fixed, not retried.
  • Frame-rate-dependent behaviour. A slow runner may expose simulation steps that depend on frame time. If the flight check finds this, it is a real bug and the fix belongs in the game.
  • Hidden local dependencies. Tests that pass only because ignored files exist will fail in CI at first. That is the point; fix them before turning protection on.
  • Lock-out. With administrators included, a broken CI blocks every merge, including fixes to the CI itself. Repair path: the owner temporarily lifts protection in GitHub settings.
  • Checkout size. About 370 MB with runtime models; use a shallow checkout.

Phases

  1. Make every existing check pass on a clean checkout: track the fit maps and fix the other ignored-folder dependencies.
  2. Add the workflow with jobs 1 to 3 on a pull request; confirm green.
  3. Add the production test hook and job 4 (startup and flight for seven variants, with screenshots).
  4. Extend the fit check to the Finch, the Finch attack variant and the Heron.
  5. Turn on auto-merge and branch protection, and update AGENTS.md and the README.
  6. Prove it: one pull request that is meant to break (a deliberate test failure) is blocked, and one clean pull request merges itself and goes live.

Success criteria

  • A direct push to main is refused.
  • A pull request with a failing test, a broken startup or a clipping pilot cannot merge, and the run shows which check and aircraft failed, with screenshots for job 4.
  • A clean pull request merges itself and Vercel publishes it, with no manual step.
  • A full run takes under about 15 minutes.
