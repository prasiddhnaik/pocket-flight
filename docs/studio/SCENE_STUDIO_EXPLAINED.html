This report documents the local implementation. It covers the execution path, serialized data, coordinate systems, clock mapping, asset dependencies, renderer lifecycle, audio mixing, persistence, and export behavior. A worked example connects those mechanisms to placing an object in a flight film.

1. Executive findings

Scene Studio is a replay-driven 3D film editor. It reconstructs an aircraft from saved state samples, adds independent scene objects, applies a camera, mixes audio, and captures the rendered canvas. The editor does not ingest an arbitrary finished MP4 as an editable 3D scene.

  • Placement is a scene-graph operation. Each object has an anchor group, an editable transform group, and visual content. World anchoring fixes its coordinate frame to the first recording’s initial aircraft position; Aircraft anchoring follows both the aircraft’s translation and orientation.
  • Timing uses multiple clocks. Flight and camera sampling use recording source time. Object transforms, visibility, embedded animation, and soundtrack scheduling use the assembled film timeline. Audio scheduling also uses an AudioContext clock.
  • Assets and instances are separate. Original file bytes live in the asset library; multiple scene objects refer to one asset ID. Loaded model templates are cached, and instances receive cloned scene hierarchies and materials.
  • Output is captured in real time. A WebGL frame is copied to a 2D canvas, title text is composited there, and MediaRecorder encodes its captured stream. Selecting 60 fps requests a capture rate; it does not ensure the GPU produces 60 unique frames per second.
  • Persistence is local. IndexedDB stores projects, replays, and assets. Portable backups embed source recordings and base64-encoded referenced asset bytes.

Evidence: ReplayStudio.tsx, replay-preview.ts, studio-scene-renderer.ts, and replay-export.ts.

2. Architecture and execution flow

The React layer owns the editing session. High-frequency state such as the playhead and running/exporting flags is held in refs, so rendering can proceed without a React update for every frame. React receives displayed time and export-phase updates approximately every 100 milliseconds.

The preview is imperative: it owns Three.js objects, controls, caches, and audio contexts. Project data remains serializable and is converted into runtime scene instances by preparation and update methods. This separation lets the same scene settings drive interactive editing and export.

Editor command
  → commit(nextProject)
  → projectRef + React project state
  → scene preparation when dependencies change
  → debounced IndexedDB save

requestAnimationFrame(now)
  → advance film playhead if running and ready
  → locateClip(project, filmTime)
  → ReplayPreview.render(sourceTime, filmTime, clip, scene)
  → ReplayVideoExport.draw(canvas, title) during export

4. Timeline and clock mapping

Let T be film time, C the selected clip’s start in the film, I its source In point, O its source Out point, and r its playback speed. The current mapping is:

clip duration D = (O − I) / r
source time t = I + clamp(T − C, 0, D) × r
project duration = sum of all clip durations

locateClip walks clips in order, accumulating their film durations. At an interior boundary it selects the next clip; the final clip also handles the project endpoint. sampleFrames uses binary search to locate neighboring source frames. The renderer linearly interpolates position and continuous state, and uses quaternion spherical interpolation for aircraft orientation.

Split duplicates the selected clip’s settings and changes its source boundaries; move swaps clips in the sequence. Object tracks belong to the project scene, so neither operation automatically remaps object keys into a specific clip.

5. Asset ingestion and instantiation

The pipeline has two separate products: a persistable asset containing original bytes, and a loaded model template from which scene instances are created.

  1. Read and classify. readAssets(files) limits the batch to 128 MiB, reads bytes, and classifies file extensions. GLB, glTF, OBJ, STL, PNG/JPEG/WebP, and supported audio extensions are recognized. Native Blender files and video clips are outside this importer.
  2. Bundle dependencies. A glTF root is bundled with the other selected files so buffers and textures can resolve locally. When glTF roots are selected, accompanying images are treated as resources rather than automatically becoming standalone image objects. GLB is the simpler portable route.
  3. Identify the asset. SHA-256 is computed over concatenated filename bytes and file bytes. The resulting hex string is the asset ID. It identifies the import bundle; filename/order changes can change the ID.
  4. Validate loadability. Visual assets go through model loading; audio assets are decoded. Successful model loading supplies embedded animation names. The imported assets are saved, then added as scene instances or soundtrack layers.
  5. Normalize the model. A bounding box supplies its center and largest dimension. The content is translated by the negative center and wrapped with uniform scale 6 / largestDimension.
  6. Instantiate. Each placed object gets a cloned loaded hierarchy, cloned materials, its own transform and anchor groups, and an AnimationMixer if clips exist.
FormatCurrent runtime pathRelevant behavior
GLB / glTFGLTFLoader.parseAsyncImports supported scene content and animation clips. Compressed-asset decoder integrations are not configured; use uncompressed GLB.

Resource resolution accepts selected local file names and paths, falling back to matching a leaf filename. Data/blob resources are allowed; unresolved resources or HTTP references cause a load error. Object URLs are revoked after loading. The model cache stores promises by asset ID, sharing both completed and in-flight loading; failed loads are removed from the cache so a retry is possible.

Dimensional implication: an imported model with a largest dimension of 120 meters is normalized to 6 meters at object scale 1. A uniform object scale of 20 restores a 120-meter maximum dimension. Centering also changes the effective placement pivot; Position identifies the centered instance frame, not the original file’s origin.

6. Coordinate frames and transforms

Three.js scene
└─ instance.anchor             // World origin OR aircraft position + quaternion
   └─ instance.group           // editable position, rotation, scale
      └─ cloned asset content  // asset centering / normalization / authored hierarchy

For column-vector notation, the hierarchy composes matrices from parent to child:

M_world = M_anchor × T_object × R_object × S_object × M_content
World anchor: M_anchor = Translation(O_world)
Aircraft anchor: M_anchor = Translation(P_aircraft) × Rotation(Q_aircraft)

The renderer receives the scene origin and currently reconstructed aircraft object. For World anchoring it uses the origin position and identity quaternion. For Aircraft anchoring it copies both aircraft position and quaternion. Y is up, position uses meters, and serialized Euler rotations are converted from degrees to radians when applied to Three.js.

The world origin is the first project clip’s source recording frame zero. It does not use that clip’s trimmed In point. Changing the first source recording can therefore change where existing World-anchored coordinates land. Y = 0 means the origin’s altitude; it does not mean the terrain height under the object.

Changing an anchor

convertAnchor translates and rotates a transform between frames while keeping scale unchanged. For the positional component:

World → Aircraft: p_air = Q_air⁻¹ × (O_world + p_world − P_air)
Aircraft → World: p_world = P_air + Q_air × p_air − O_world

The editor converts the base transform at the current playhead and each transform key at that key’s film time. Rotation is composed using quaternions and converted back to Euler degrees. This aims to preserve the pose at conversion samples; interpolation between converted keys need not reproduce the entire previous continuous path.

Precision boundary: the conversion handler samples interpolated aircraft position but passes the earlier saved frame’s quaternion. The renderer uses the interpolated quaternion and may also apply suspension displacement. Thus the pure conversion function’s round-trip test establishes its mathematics for a supplied pose; it does not prove exact UI pose preservation at every between-frame playhead position.

Default placement

spawnPosition computes aircraft position relative to the project origin, then adds [8, 2, 0]. New visual objects default to World anchoring. This is an offset in world axes, not eight meters along the aircraft’s local right direction. Objects default to visibility from film zero through the film end.

Evidence: studio-scene.ts — convertAnchor; ReplayStudio.tsx — changeObject and spawnPosition; studio-scene-renderer.ts — update.

7. Selection and edit transactions

Viewport selection converts a pointer position into normalized device coordinates, builds a camera ray, and recursively intersects visible instance roots. Every mesh descendant is tagged with sceneObjectId, allowing a child-mesh hit to select the owning object. The handler ignores non-left-button events, pointer movement above five pixels, and active gizmo axes so orbiting or manipulation is not treated as a simple selection click.

TransformControls attaches to the editable instance group. During a drag, orbit controls are disabled and the renderer skips overwriting that object’s transform from serialized data. On mouse-up, its local pose is read, scale components are clamped to at least 0.001, and the editor commits the transform or a keyframe.

commit stops playback, stores the previous project in an undo stack, clears redo, updates the project timestamp and state, clamps the playhead to the new duration, and sets the save status. History is capped at 40 previous project snapshots. Commits are ignored while export is running or preparing.

Object selection switches to Scene mode and opens Object settings. Gizmos are enabled only when the object is selected, visible, and unlocked. Numeric fields commit finite values on blur or Enter, constrained to their configured bounds. Snapping is 1 meter for translation, 15 degrees for rotation, and 0.1 for scale.

Evidence: replay-preview.ts — pointerUp, TransformControls handlers, and render; ReplayStudio.tsx — commit and historyStep; StudioScenePanels.tsx — NumberField.

8. Object and embedded animation

Transform tracks

setTransformKey stores a copied pose, rounds its timestamp to milliseconds, replaces an existing key within the configured near-time tolerance, and sorts the track. The editor creates keys on transform edits when Auto keyframes is enabled or the object already has keys; otherwise it replaces the static transform.

sampleTransform holds the first and last poses outside the keyed interval. Between two keys it interpolates position and scale component-wise, converts Euler rotations to quaternions, uses spherical interpolation for rotation, then converts back to Euler angles. This avoids directly interpolating Euler components across angle wrap, although the track does not store an explicit multi-turn rotation count.

u = (T − t₀) / (t₁ − t₀)
Linear: w = u
Smooth: w = u² × (3 − 2u)
Hold: w = 0 until the next key; at its endpoint w = 1
Position / scale: value = value₀ + w × (value₁ − value₀)

The earlier key’s easing controls the outgoing segment. Aircraft anchoring composes the sampled object pose beneath the moving aircraft frame. Static color, opacity, roughness, metalness, and light intensity are not transform-keyframe channels.

Visibility and embedded clips

An instance is active when its visible flag is true and film time is inside its start/end interval, clipped to project duration. Visibility does not derive from transform keys. The active test includes the object’s end instant; soundtrack scheduling treats its end as exclusive.

Each animated imported instance receives its own mixer and actions. Changing the selected embedded clip stops the previous actions and starts the new one. On each update the mixer is sampled at max(0, T − object.start) × animationSpeed, modulo clip duration when looping, or clamped near the final frame otherwise. This supports seeking without integrating animation incrementally. A newly imported asset selects its first animation when one exists; the inspector can select None.

Evidence: studio-scene.ts — segment, sampleTransform, setTransformKey; ReplayStudio.tsx — changeObjectPose and addAsset; studio-scene-renderer.ts — update.

9. Camera reconstruction

The preview uses a PerspectiveCamera with a default 48-degree field of view, 16:9 aspect, near plane 0.2, and far plane 11,000. Preset shots choose offsets, scale them by the aircraft’s camera scale, and rotate them around world Y using aircraft yaw. Presets enforce a minimum terrain clearance of three meters for the camera.

Custom camera keys store source time, position, target, field of view, and easing. Capture records the current view relative to either the fixed project origin or aircraft position. Position, target, and field of view interpolate using the same segment easing logic as object tracks.

Camera and object anchors have different rotation semantics. An Aircraft-anchored object inherits the aircraft quaternion. A custom aircraft-tracking camera adds the aircraft position to its stored position and target offsets, without rotating those offsets by the aircraft quaternion. It follows translation while preserving those offsets in world orientation.

Changing a camera anchor converts key positions and targets using translation only; the editor explicitly supplies an identity quaternion for that conversion. Capture at source time is owned by the selected flight clip, so duplicate and split operations retain that clip’s key data.

In Scene mode, OrbitControls owns the view; simply orbiting does not save a camera path. Capturing a key selects the custom camera. During playback/export, the renderer samples saved camera keys or uses the selected preset. Custom camera positions do not pass through the preset terrain-clearance clamp, so authored camera paths need inspection for terrain crossings.

Evidence: replay-preview.ts — camera initialization, captureCamera, and render; ReplayStudio.tsx — edit and captureCamera; studio-scene.ts — sampleCamera.

10. Per-frame rendering pipeline

  1. Locate and sample the source. Resolve the film time to a clip and source time, find adjacent recorded frames, and interpolate the aircraft pose.
  2. Reconstruct aircraft visuals. Apply paint, suspension, gear/wing/propeller visibility, control surfaces, propeller motion, and supported jet effects. Continuous fields interpolate; discrete state uses the selected neighboring frame.
  3. Resolve the camera. Use the editing view, source-time camera track, or shot preset.
  4. Update the world. Interpolate recorded world time; use recorded/day/night lighting and project exposure.
  5. Update scene instances. Apply visibility, anchor transforms, sampled object poses, appearance changes, and embedded animation time.
  6. Update interaction and audio. Attach/detach gizmos, show editing-only helpers, and schedule soundtrack plus aircraft audio.
  7. Draw WebGL. Render the scene through the perspective camera. During export, copy that result to the capture canvas.

The renderer requests antialiasing and high-performance GPU preference, uses pixel ratio 1, PCF soft shadows, and ACES filmic tone mapping. Preview normally uses 1280 × 720 internal resolution; export selects 720p or 1080p. CSS viewport sizing maintains the 16:9 display independently of canvas pixels.

Scene readiness combines world, model, and soundtrack preparation. Generation counters suppress obsolete completion state after later edits or cancellation. Instance preparation avoids duplicating an instance if another preparation completed while an asset was loading.

Removing an imported instance disposes its cloned materials but retains shared template geometry/textures. Removing a primitive disposes its geometry. Disposing the renderer removes instances and disposes cached templates and their textures. This ownership distinction permits multiple instances to share immutable resources.

Evidence: replay-preview.ts — constructor, prepareScene, render, dispose; studio-scene-renderer.ts — prepare, update, remove, dispose.

11. Audio pipeline

StudioSoundtrack decodes imported audio to AudioBuffers and caches them by asset ID. A playback source and GainNode are created per active sound layer. The gain connects both to the normal audio output and to a MediaStreamAudioDestinationNode used for export. The aircraft’s captured audio track is routed into that capture destination too.

elapsed = filmTime − layer.start
audioSourceTime = layer.offset + elapsed
looped offset = audioSourceTime mod audioBuffer.duration
gain target = layer.volume × max(0, min(fadeInFactor, fadeOutFactor))

Audio is active only while playback is running and inside the layer interval. Non-looping audio stops when its source duration is exhausted. Sources are restarted if the placement signature changes or if estimated audio time differs from requested source time by more than 0.3 seconds. Fade gain uses setTargetAtTime with a 0.015-second time constant rather than abrupt per-frame gain jumps.

Pausing stops active layer sources. The next playback starts from the playhead-derived source offset. Imported audio is not automatically pitch- or time-stretched to match flight clip speed. Scene soundtrack layers remain on film time, while aircraft sound is generated from the sampled aircraft state and clip volume.

Evidence: studio-soundtrack.ts — start, prepare, update, pause; replay-preview.ts — startAudio and audio update.

12. Video capture and finalization

Export prepares all referenced aircraft, scene assets, and audio; sets the renderer resolution; renders the first frame with editing disabled; resets film time to zero; and starts recording. Playback then advances from requestAnimationFrame elapsed time.

Three.js WebGL canvas
  → 2D capture canvas (drawImage, fitted and centered)
  → clip title overlay drawn in screen coordinates
  → canvas.captureStream(requested fps)
  + cloned mixed audio track
  → MediaRecorder
  → data chunks → Blob → object URL → download / review

Export phase transitions are idle → recording → finishing → ready, with an error path and explicit cancellation. MIME candidates are checked in this order: H.264/AAC MP4, generic MP4, VP8/Opus WebM, then generic WebM. The output extension follows the recorder’s chosen MIME type.

The screen-space title is drawn after the 3D scene, so it is not subject to scene depth or object occlusion. Imported images remain 3D planes and do not receive this screen-space treatment. No editing grid, transform gizmo, or light marker is included when the preview is rendered with editing disabled.

This capture path samples real-time playback rather than rendering an indexed frame sequence offline. A long frame delay advances the playhead by elapsed time; visual samples may be skipped. The duration bitrate heuristic and byte limit do not establish a quality or memory-performance guarantee.

Evidence: ReplayStudio.tsx — exportVideo, animation loop, visibility handler; replay-export.ts — start, draw, finish, releaseRecorder.

13. Persistence and portable backups

ReplayLibrary opens IndexedDB database pocket-flight-studio at version 2, with replays, projects, and assets stores keyed by ID. Database upgrades create missing stores. A blocked upgrade reports that other Pocket Flight tabs must close; a version-change event closes the current database connection.

Project changes trigger a 500-millisecond debounce. Saves are serialized through a promise queue. A failed job does not permanently block later jobs, and the saved-status update is accepted only for the current project timestamp. Storage failures leave the in-memory edit open and expose a backup-oriented error message.

When a project references assets, its save uses a transaction covering both projects and assets. All required IDs are checked; a missing dependency aborts the transaction. Restore can insert the included assets and project atomically, and tests verify rollback when a dependency is missing.

{
  "type": "pocket-flight-studio-bundle",
  "version": 1,
  "project": { /* clips, copied recordings, scene settings */ },
  "assets": [ /* referenced assets, original bytes encoded as base64 */ ]
}

packProject includes only assets referenced by scene objects and soundtrack layers. unpackProject checks the envelope/version, validates the project, decodes asset bytes, validates assets, and verifies that referenced IDs exist in the bundle. Assets elsewhere in the library but unused by the film are not included.

Browser saves belong to the site origin and browser profile. Clearing site data can remove them. Backups have base64 expansion of roughly one-third for binary payloads, plus JSON overhead, and packing creates additional in-memory representations. Treat an exported video and an editable backup as different deliverables.

Evidence: replay-library.ts, studio-assets.ts — packProject/unpackProject; ReplayStudio.tsx — persistence effect and queue.

14. Worked example: placing a tower into the film

The goal is a stationary tower that appears beside the recorded route during a fly-by. The values below are an illustrative scene specification, not coordinates measured from a particular replay.

Numerical placement calculation

Assume scene origin O = [100, 50, 200] meters and tower Position p = [30, −5, −80]. With World anchoring, the centered tower instance is placed at O + p = [130, 45, 120]. If its normalized maximum dimension is 6 meters, uniform Scale = 8 produces a maximum dimension of approximately 48 meters before any subsequent embedded deformation.

A vertically centered 48-meter tower would extend approximately 24 meters below its center if its geometry is symmetric about that center. To rest its base on terrain, account for its actual bounding-box extent and local ground height. Center normalization means blindly entering the ground height as Position Y can bury half the model.

How a placed object reaches the exported pixels

The object is visible when its interval is active, its visible flag is true, and its geometry falls inside the camera frustum without being hidden by other geometry. The GPU applies the object/world transform, camera view transform, and perspective projection, then shades and depth-tests the geometry. A valid object record alone does not guarantee it appears in the shot.

To attach the tower or a smaller prop to the aircraft, change to Aircraft anchoring. Its position then becomes a local offset transformed by the aircraft orientation. That changes its reference frame, not the recorded flight path or gameplay collisions.

15. Implementation limits and implications

Observed behavior or boundaryTechnical implication
Flight state is reconstructed from saved samples.Adding scene objects does not re-run flight physics or add gameplay collision interactions.
Scene objects span the overall project.Reordering, trimming, or changing the first source can affect animation alignment and world placement; inspect the result after structural edits.
Model templates share geometry/textures; instances clone materials.Repeated assets avoid repeated decoding, but still add scene nodes, draw submissions, and potentially animation mixers. No explicit GPU-instancing path is used for imported scene instances here.
128 MiB is an import-byte limit.Decoded textures, geometry, clones, and audio buffers can consume substantially more memory. File size does not measure scene rendering cost.
Appearance is static; keys store transforms.Arbitrary material, opacity, or light-intensity animation requires extending the data model, inspector, and runtime sampling.
Camera tracking and object anchoring differ.Do not assume an aircraft-tracking camera banks with an attached object; authored offsets remain world-oriented for custom cameras.
Snapshot conversion has sampling differences.Exact anchor conversion deserves an integration check at between-frame positions, particularly around fast aircraft rotation.
Export uses browser real-time recording.Frame cadence, codec availability, and output quality depend on the browser and hardware. The focused tests do not validate capture fidelity.
Stored replay fields exceed the studio preview’s explicit reconstruction path.The replay schema includes debris and mission-ring state, but this preview does not reconstruct those entities from the saved fields. Do not infer full gameplay-state reproduction from schema presence.
Browser-local storage and base64 backups.A project needs a portable backup for movement between profiles/devices; large backup creation has additional memory cost.

If these capabilities are extended, keep the same separation: serialize intent in the project model, validate it, expose it through the inspector, sample it in the runtime, include its dependencies in backup packaging, and add focused tests for its behavior. This is an architectural implication of the current design, not a change implemented by this report.
